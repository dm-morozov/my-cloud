# Аудит My Cloud и переноса на Selectel

Дата: 2026-10-08. Статус: аудит выполнен; My Cloud на новом сервере ещё не опубликован.

## Вывод

Перенос реалистичен без переписывания приложения. В репозитории уже есть Django API,
PostgreSQL-модели, React SPA и тесты. Для демонстрации предлагается отдельный
Docker Compose проект `mycloud` на существующем VDS, за серверным Nginx.
Оценка ресурсов предварительная: совместную нагрузку двух проектов нужно измерить.

## Доступы

- SSH-вход на новый VDS подтверждён существующим локальным ключом Selectel.
- Для текущего запуска достаточно SSH и права управлять Docker/Nginx.
- Пароль кабинета Selectel и API-токен для этого не нужны.
- Для публичного адреса понадобится выбранный домен и доступ к его DNS.
- Для переноса существующих пользователей и файлов нужен доступ к старому
  серверу или резервная копия PostgreSQL и каталога media.
- Если достаточно новой демонстрации, можно создать отдельную базу и тестовые данные.

Приватные ключи, пароли и содержимое рабочих .env в документацию не включаются.
Позднее стоит выделить отдельного пользователя развёртывания; root сейчас имеет
доступ ко всем проектам на этом VDS.

## Находки в приложении

### Перед публичным запуском

1. В README опубликованы реквизиты тестового административного аккаунта.
   На новом окружении нужны новые секреты и отдельный непривилегированный
   демо-пользователь. Удаление пароля из документации не отменяет необходимость
   сменить его, если аккаунт существует.
2. Старый пример Nginx напрямую раздаёт `/media/`. При знании пути это обходит
   проверки владельца в `apps/files/services.py`. На новом сервере не включать
   такую раздачу: скачивание через защищённый API или внутренний X-Accel-Redirect.
3. `apps/files/public_api.py` и `apps/files/api.py` допускают `inline=true` для
   произвольного типа файла. Загруженный HTML на домене приложения может
   исполняться в его origin. Ограничить inline безопасным списком типов,
   остальные отдавать вложением; для расширенного просмотра рассмотреть
   отдельный домен без сессионных cookies.
4. В API загрузки нет проверки размера файла и квоты пользователя. Заявленные
   на главной странице 500 МБ присутствуют в старом Nginx-примере, но не являются
   гарантией приложения. Для демо нужны лимиты в API и proxy, общая квота и очистка.
5. Отдельный демо-режим, создание демо-данных и их сброс в исходниках не обнаружены.
   Сейчас тестовый аккаунт описан в README. Нужно выбрать сценарий демонстрации.
6. Для нового домена настроить ALLOWED_HOSTS, CSRF, HTTPS и secure cookies.
   `manage.py check --deploy` на локальном .env показывает предупреждения
   о DEBUG, SECRET_KEY, secure cookies, SSL redirect и HSTS.
   Это состояние локального окружения, не проверка настроек старого сервера.
7. Login реализован через DRF APIView; отдельной явной CSRF-защиты входа не видно.
   Перед публикацией проверить login CSRF и cookie flow отдельным тестом:
   стандартные API-тесты не доказывают корректность CSRF.

### Эксплуатация

- Dockerfile, Compose и воспроизводимого контейнерного запуска пока нет.
- Данные PostgreSQL и media должны сохраняться в разных постоянных volumes.
- Бэкапы базы и файлов должны образовывать согласованную копию и храниться
  вне этого VDS; до переноса нужно проверить восстановление.
- Для общего сервера задать пределы памяти, ротацию логов и healthchecks.
- Доступ к PostgreSQL и Gunicorn извне не публиковать.
- Frontend имеет отслеживаемый `yarn.lock`; сборку контейнера привязать к нему.
- Две backend-зависимости используют нижнюю границу версии вместо фиксации.
  Зафиксировать воспроизводимый набор зависимостей перед релизом.

## Предлагаемое развёртывание

```text
HTTPS / выбранный домен
  -> существующий Nginx на сервере
  -> 127.0.0.1:18081 (предлагаемый порт, свободен при проверке)
  -> gateway контейнер My Cloud: React build + proxy /api/ и /admin/
  -> backend контейнер: Gunicorn + Django
  -> database контейнер: отдельный PostgreSQL
```

Папка сервера: `/srv/projects/mycloud`. Compose project name: `mycloud`.
Отдельные сеть, база, секреты и volumes. Gateway не монтирует пользовательское
media для публичной раздачи. Django static можно отдавать через gateway.
Изоляция Compose разделяет ресурсы проектов, но CPU, диск и ОС остаются общими.

Для начала оценить бюджет около 256 MiB для backend, 256 MiB для PostgreSQL
и 64 MiB для gateway, затем подобрать значения по измерениям. Это гипотеза,
не проверенный production sizing. Начать с одного Gunicorn worker.
Сборку образов предпочтительно делать вне этого маломощного VDS.

## Структура и название

Текущее разделение `backend/apps/users`, `backend/apps/files`, `services`,
`serializers`, `api` достаточно понятно. Сервисные функции здесь уместны:
добавлять классы только ради ООП не требуется. Позже полезнее улучшить границы
транзакций, обработку ошибок файлового хранилища и покрытие сценариев.

Для продукта подходит рабочее название **My Cloud**, папка и репозиторий
`my-cloud`, серверный каталог `mycloud`. Учебную историю сохранить в
`docs/netology`, основной README переписать вокруг возможностей и запуска.
Локальная папка пока не переименована: сначала обновить ссылки, настройки IDE
и прикрепление проекта в приложении. Переименование не является условием деплоя.

Статус и backlog в docs устарели: всё ещё описывают инициализацию, хотя API и SPA
уже реализованы. После запуска синхронизировать их с фактическими результатами;
важные выводы хранить в Git, временные исследования в `docs/workspace`.

## Направление интерфейса

Оценка сделана по исходникам, без визуальной проверки живой страницы.
Главная использует градиентный заголовок, универсальные карточки, emoji,
подъёмы при наведении и рекламные показатели. Они дают мало информации о
реальной работе хранилища. «500 МБ» должно соответствовать реальным лимитам.

Предлагаемая следующая версия: спокойный интерфейс рабочего инструмента,
графитовый текст, светлая тёплая основа, один выразительный акцент,
согласованные SVG-иконки и хорошо выстроенная типографика. Главная показывает
реальный фрагмент файлового интерфейса; хранилище получает ясную таблицу,
прогресс загрузки, поиск, пустые состояния и понятные действия с файлами.
Мобильный интерфейс проверить отдельно. Начать с одного прототипа главной
и хранилища, затем переносить визуальный язык на остальные экраны.
